## 1. Краткий вывод о реализуемости

**Идея реализуема.** Самый разумный путь — **собственное ядро проекта и рендера** (граф операций как единственный источник истины), к которому Surge XT и другие компоненты подключаются как **узлы рендера** через стабильные интерфейсы. Audacity в роли ядра или движка не подходит.

Ключевые выводы:

1. **Audacity нельзя делать фундаментом автоматизации.** ✅ Вышел Audacity 4.0.0 (3 сентября 2026), и в нём **нет scripting pipe и Macro Manager** («планируется в будущих релизах», без даты). Скриптинг Audacity 3.x (`mod-script-pipe`) работает только при запущенном GUI-экземпляре. Свою роль в проекте Audacity может сохранить только как внешний редактор: файл уходит туда и возвращается обратно с записью происхождения.
2. **Surge XT ценен как источник качественного DSP, а не как среда.** ✅ Python-биндинги `surgepy` дают оффлайн-рендер быстрее реального времени, доступ ко всем параметрам, загрузку и сохранение патчей, редактирование MSEG-огибающих, формулы и матрицу модуляции, а также обработку входного аудио (`processMultiBlockWithInput`). Для управления в реальном времени есть OSC. При этом Surge — нотный полисинтезатор: у него нет таймлайна, слоёв-клипов и работы с сэмплами как с материалом.
3. **Для MVP не нужен потоковый realtime-движок, но архитектура должна его допускать.** 💭 Hitmarker длится 50–500 мс (✅ в Trailblazer попадания 75–110 мс, убийства 0,62–0,75 с), и перерендер всего звука занимает миллисекунды или десятки миллисекунд. Поэтому MVP строится на **render-on-change**. Узлы при этом сразу пишутся с потоковым (блочным) контрактом, чтобы режим **real-time preview** добавлялся без переписывания движка (раздел 6.12).
4. **ИИ должен работать с типизированными операциями над графом проекта** (`set_param`, `add_layer`, `set_envelope_points`…), а не с shell-командами. Каждое предложение ИИ — это changeset: его можно прослушать в режиме A/B, принять частично или откатить. Цели предложения («атака не хуже исходной», «хвост короче 250 мс») проверяются измерениями после рендера. Модель-провайдер заменяема; облачная модель не обязательна (раздел 6.5).
5. **Лицензирование.** ✅ Surge XT, его библиотеки `sst-*`, `pedalboard` и `DawDreamer` распространяются по GPL-3.0. ForgeSound выпускается под **GPL-3.0-or-later** (решение владельца); лицензия каждой зависимости, плагина и сэмпла учитывается отдельно.
6. **Trailblazer уже содержит работающую «ручную» версию задачи** (✅ аудит в разделе 2.4): генератор `tools/f10_hitsounds.py` (6 стилей × (1 попадание + 5 ступеней убийства) = 36 WAV), анализ маскировки выстрелами `tools/f10_gunmask.py` и калибровку громкости, принятую владельцем на слух. ForgeSound должен воспроизвести эти соглашения в профиле экспорта, а не менять мод.
7. **NixOS реальна, но не «из коробки».** ✅ Пробная сборка `surgepy` через Nix выявила четыре проблемы: старый вложенный pybind11 против CMake 4; конфигурация Surge требует целей плагинов; в main JUCE 8 нужен `fontconfig`; скрипт сборки LuaJIT требует `patchShebangs`. Все решены в деривации ForgeSound. ✅ Нужное API MSEG есть только в ветке main Surge, не в релизе 1.3.4. ✅ Генератор случайных чисел Surge засевается от часов, поэтому часть патчей принципиально невоспроизводима без доработки (разделы 2.1, 2.5).

**Выбор (подтверждён владельцем):** вариант **C (гибридная модульная платформа)**: ядро по образцу варианта B (собственный граф, таймлайн, огибающие, вариации, ИИ-операции) плюс адаптеры к Surge XT и плагинам. Обоснование — в разделах 5 и 6.

### 2.1 Surge XT

Репозиторий: <https://github.com/surge-synthesizer/surge> · лицензия ✅ GPL-3.0 (`LICENSE`).

#### Способы интеграции

| Интерфейс | Что даёт | Статус и источник |
|---|---|---|
| **Плагины VST3 / CLAP / LV2 + standalone** | Полный синтезатор в любом хосте | ✅ nixpkgs `surge-xt` 1.3.4 собирает VST3, LV2, CLAP и standalone (`pkgs/by-name/su/surge-xt/package.nix`). VST2-сборки распространять нельзя (README) |
| **Surge XT Effects** (отдельный плагин) | Эффекты Surge как обычный аудиоэффект: подходит для обработки сэмплов | ✅ `src/surge-fx`, опция `SURGE_BUILD_FX` |
| **Surge XT CLI** | Безголовый синтезатор с аудиоустройством, MIDI и OSC | ✅ `src/surge-xt/cli/cli-main.cpp`: флаги `--osc-in-port`, `--osc-out-port`, `--init-patch`, `--audio-input-ports`, `--sample-rate`, `--buffer-size`, `--no-stdin` |
| **OSC** | Управление параметрами, нотами, патчами, тюнингом и вейвтейблами в реальном времени; изменения отражаются в OSC out | ✅ `resources/surge-shared/oscspecification.html`, `src/surge-xt/osc/OpenSoundControl.cpp` |
| **Python (`surgepy`)** | Оффлайн-рендер в numpy, полный доступ к параметрам, патчи, MSEG, формулы, модуляция, обработка входного аудио | ✅ `src/surge-python/surgepy.cpp`, сборка через `-DSURGE_BUILD_PYTHON_BINDINGS=ON` (README, раздел «Building and Using the Python Bindings») |
| **Rust (`surge-rs`)** | Экспериментальные биндинги | ✅ сабмодуль `surge-synthesizer/surge-rs`, опция `SURGE_BUILD_RS` по умолчанию OFF. 💭 Считаю незрелыми |
| **Библиотеки `sst-*`** | Фильтры, эффекты, вейвшейперы и базовые DSP-блоки Surge как отдельные C++-библиотеки (header-only) | ✅ `sst-filters`, `sst-effects`, `sst-waveshapers`, `sst-basic-blocks`: все GPL-3.0 (`LICENSE.md`) |

**Важно:** ✅ пакета `surgepy` на PyPI нет: `pypi.org/pypi/surgepy` отвечает 404. Пакет `surge-py` на PyPI — **посторонний проект** (решатель энергосетей, лицензия PolyForm Noncommercial). Значит, `surgepy` придётся собирать из исходников, и это удобно делать через Nix-деривацию.

#### API `surgepy` (подтверждено по исходнику)

- `surgepy.createSurge(sampleRate)` создаёт экземпляр синтезатора.
- `getControlGroup(...)`, `getParameterName`, `getParamMin/Max/Def/Val`, `getParamDisplay`, `getParamInfo`, `setParamVal` — полный программный доступ к параметрам. Также доступны `setExtend`, `setTempoSync`, `setAbsolute`, `setDeactivated`, `setDeform` и опции портаменто.
- `playNote`, `releaseNote`, `pitchBend`, `channelController`, `polyAftertouch`.
- `process` / `getOutput` и `createMultiBlock` / `processMultiBlock` — оффлайн-рендер блоками в numpy-массив.
- **`processMultiBlockWithInput(in, out)`** — рендер с входным аудио. В связке с осциллятором *Audio Input* или эффектом *Audio Input* это даёт обработку сэмпла фильтрами и FX Surge (тест `test_render_note_with_input`).
- `loadPatch` / `savePatch` (`.fxp`) и `getPatch()` (параметры в виде Python-словаря) — сохранение и воспроизведение состояния.
- `getMSEG` / `setMSEG` с сегментами (`duration`, `v0`, `cpduration`, `cpv`, `type`, `useDeform`…) — программное редактирование многосегментных огибающих. ✅ В репозитории свежие тесты: round-trip MSEG через патч, вставка и удаление сегментов, loop points.
- `getFormula` / `setFormula` / `checkFormula` — Lua-модуляторы (Formula LFO).
- `setModDepth01`, `getAllModRoutings` — матрица модуляции.

#### Что можно использовать, не написав ни строчки синтезатора

✅ Осцилляторы: Classic, Modern, Wavetable, Window, Sine, FM2, FM3, String (физмодель струны), Twist (порт Mutable Plaits), Alias, S&H Noise, Audio Input.
✅ Эффекты: Delay, Reverb 1/2, Phaser, Flanger, Chorus, Distortion, WaveShaper, Ring Mod, Freq Shift, EQ (3-полосный параметрический и 11-полосный графический), Conditioner, **Resonator**, **Combulator**, Nimbus, Bonsai, Treemonster, Convolution, Vocoder, Rotary, BBD Ensemble, а также наборы Airwindows и ChowDSP (каталог `src/common/dsp/effects`).
💭 Для индустриальных hitmarker'ов особенно полезны String и Twist (металлические и перкуссионные модели), Resonator и Combulator (окраска шумов и транзиентов), Distortion/WaveShaper (вес и плотность), а также MSEG для точной формы огибающих.

#### Ограничения

- 💭 Архитектура нотная: 2 сцены × 3 осциллятора, 2 фильтра на сцену, 16 FX-слотов. Нет понятия «клип на таймлайне» и нет one-shot сэмплера: вейвтейбл — не проигрыватель сэмплов.
- ✅ OSC: значения параметров нормализованы в 0..1, все числа передаются как float. OSC доступен только в JUCE-обёртке (плагин, standalone, CLI), в `surgepy` его нет. CLI выводит звук **в аудиоустройство, а не в файл**, поэтому для оффлайн-рендера нужен `surgepy` или хостинг плагина.
- 💭 Воспроизводимость: генераторы шума, S&H, случайные LFO и «дрейф» осцилляторов могут давать разный результат от прогона к прогону. Нужно проверить бит-в-бит повторяемость рендера через `surgepy` и при необходимости фиксировать seed или исключать такие источники случайности (этап 0 плана).
- 💭 API `surgepy` развивается (MSEG-методы появились недавно), поэтому коммит Surge нужно закреплять (pin), и это естественно делается во flake.
- ✅ Лицензия: GPL-3.0. Сторонние вейвтейблы и патчи лежат в `resources/data/*_3rdparty` под собственными условиями. 💭 Встроенный контент Surge в проектах ForgeSound лучше не использовать (только Init-патчи и собственные патчи), чтобы не наследовать неясные условия.

#### Уточнено в версии 2 (по исходному коду и пробной сборке)

- ✅ **Релиз 1.3.4 против main.** В `surgepy.cpp` релиза `release_xt_1.3.4` нет `getMSEG`/`setMSEG`, `getFormula`/`setFormula`, `setExtend`/`setDeform`/`setTempoSync` и других «особенностей параметров». Они есть только в main (проверено на `dab78c6`). Управление MSEG-огибающими Surge с таймлайна ForgeSound требует **закреплённого коммита main**; релиз 1.3.4 годится как запасной вариант без MSEG.
- ✅ **Случайность.** `SurgeStorage::RNGGen` засевается от `std::chrono::system_clock` (`src/common/SurgeStorage.h`), публичного способа задать seed нет (`seed_rand` закомментирован). Также от `std::random_device` засеваются `RandomModulationSource`, `MSEGModulationHelper` и часть эффектов ChowDSP. В `SurgeSynthesizer` есть `srand(time(nullptr))`. Значит, всё, что берёт случайность из этих источников (S&H/шум-модуляторы, случайные LFO, дрейф и фаза некоторых осцилляторов, Tape/Spring Reverb), **не будет повторяться бит-в-бит**. ✅ **Измерено в пробном прогоне этапа 0** (релиз 1.3.4, 11 типов осцилляторов, два рендера в одном процессе и рендер в новом процессе): при параметре осциллятора `retrigger = Off` (значение по умолчанию — случайная начальная фаза) **не совпадает ни один тип**, расхождения от −5 до −27 дБ. При `retrigger = On` **бит-в-бит совпадают 9 из 11**: Classic, Sine, Wavetable, FM2, FM3, Window, Modern, Twist, Alias. Остаются случайными **S&H Noise** и **String** (шумовое возбуждение). Варианты решения — в разделе 6.3.
- ✅ **Каталоги данных.** Заводские данные Surge ищутся через переменную окружения `SURGE_DATA_HOME` (`SurgeStorage::getOverrideDataHome`), иначе по стандартным путям. Пользовательский каталог определяется от `HOME` и XDG-путей. Воркер ForgeSound запускается с `SURGE_DATA_HOME` из Nix-store и временным `HOME`, чтобы личные пресеты пользователя не влияли на рендер.
- ✅ **Размер блока** задаётся при компиляции (`SURGE_COMPILE_BLOCK_SIZE`, по умолчанию 32 сэмпла).

### 2.2 Audacity

Репозиторий: <https://github.com/audacity/audacity> · лицензия ✅ GPL-3.0, большинство файлов GPL-2.0-or-later (`LICENSE.txt`).

#### Состояние проекта (критично для решения)

- ✅ Ветка `master` — это **Audacity 4** (`version.cmake`: 4.0.0, новый UI на Qt/Muse). Старый код лежит в каталоге `au3/`, ветка для 3.x называется `audacity3`.
- ✅ Changelog 4.0.0 (<https://www.audacityteam.org/changelog/>, дата релиза 3 сентября 2026): **Macro Manager и scripting pipe недоступны в 4.0**, их обещают вернуть в будущих релизах. Также отсутствуют хостинг LADSPA и VAMP, Time Tracks, Note/MIDI-дорожки, Mixer и Play-at-speed. Nyquist-плагины, VST3 и LV2 (на Linux) поддерживаются. Формат `.aup4` односторонний: сохранить обратно в `.aup3` нельзя. Источники: [changelog](https://www.audacityteam.org/changelog/), [linuxiac](https://linuxiac.com/audacity-4-0-audio-editor-released-with-redesigned-qt-interface-new-editing-model/), [digitalproduction](https://digitalproduction.com/2026/09/08/audacity-4-rebuilds-the-fast-audio-editor/).
- ✅ В новом коде (`src/`) нет ссылок на `mod-script-pipe`. Взамен появился зачаточный API расширений (`src/extensions/api`: `AudioTransformApi.create(library, operation, contexts)` на QJS и загрузка нативных библиотек). 💭 Он новый, документации почти нет — опираться на него рано.
- ✅ В nixpkgs master пакет `audacity` уже 4.0.0, а в стабильном канале **nixos-26.05 — 3.7.7** (проверено `nix eval`). ForgeSound от скриптинга Audacity не зависит, поэтому подходят обе версии.

#### Автоматизация в Audacity 3.x (`mod-script-pipe`)

- ✅ Модуль `au3/modules/scripting/mod-script-pipe`. Каналы на Linux: `/tmp/audacity_script_pipe.to.<uid>` и `/tmp/audacity_script_pipe.from.<uid>` (`au3/scripts/piped-work/pipe_test.py`). Скрипт требует, чтобы *Audacity уже был запущен и модуль был включён*.
- ✅ Команды с именами вида `Command:` и параметрами, например `Import2`, `Export2` (`au3/src/commands/ImportExportCommands.cpp`), выделение, эффекты и `GetInfo`.
- 🔎 Модуль по умолчанию выключен и включается в настройках (Preferences → Modules) с перезапуском. В AppImage-сборках 3.0.x он не работал ([forum](https://forum.audacityteam.org/t/mod-script-pipe-is-missing-cant-use-scripting-api/63468)).

| Пакетная обработка через pipe | **Не рекомендуется** | В 4.0 pipe отсутствует; в 3.x нужен запущенный GUI, а состояние живёт в чужом проекте — это ломает воспроизводимость |

**Как избежать зависимости от GUI-автоматизации:** 💭 только файловый обмен. ForgeSound экспортирует WAV во временную рабочую папку, открывает Audacity командой `audacity file.wav`, отслеживает изменение файла (inotify) и импортирует результат как новую неизменяемую ревизию ассета с хешем родителя. Никаких pipe-команд и кликов по интерфейсу.

#### Движок и сборка

- Мод работает **только на UZDoom 5.0.3**; GZDoom 4.14.2 его не компилирует (`CLAUDE.md`, `docs/KNOWN_ISSUES.md` K-16). В nixos-26.05 пакет `uzdoom` — **4.14.3**, то есть для игровой проверки на NixOS нужен UZDoom 5 (AppImage или переопределённая деривация; раздел 6.11).

|---|---|---|
| Ogg Vorbis | 387 | 22,05 / 32 / 44,1 / 48 кГц, моно и стерео |
| WAV (RIFF) | 40 | в основном 44,1 кГц моно 16 бит; встречаются 11 025 и 22 050 Гц |

Вывод: **тип файла определяется по сигнатуре, а не по расширению**. Иначе 12 DMX-файлов будут считаться повреждёнными WAV.

#### Лицензии контента мода

`README.md` мода: оригинальный Trailblazer разрешает повторное использование «с указанием авторства»; Extended — «неофициальный и некоммерческий». Атрибуция сторонних звуков записана комментариями прямо в `SNDINFO.txt` (например, `//Dparke\Freesound`). Значит:

- звуки Trailblazer **не попадают в распространяемую библиотеку ForgeSound**;
- ForgeSound читает их на месте, по пути к локальной копии мода, как «внешнюю справочную библиотеку» (лицензия: «локальная, не для распространения»): для анализа, контекстного прослушивания (выстрелы) и как референсы громкости;
- производные звуки, сделанные на их основе, наследуют пометку «не для распространения вне мода», пока владелец не решит иначе.

#### Что из этого следует для ForgeSound

1. Профиль экспорта Trailblazer: имена `TBHIT???` / `TBK???N`, WAV 16 бит моно 44,1 кГц, комплект «1 попадание + 5 ступеней» на стиль, громкость в той же мере (`a_rms`) относительно **текущего файла того же имени**, проверка маскировки тем же методом, что `f10_gunmask.py` (раздел 6.9).
2. Предпрослушивание в профиле Trailblazer: попадание — на нескольких высотах из диапазона `HitPitch`, убийства — серией x1…x5, по желанию — поверх выстрелов мода.
3. ⚠️ `f10_hitsounds.py` при повторном запуске перезапишет файлы стиля. Если звуки ForgeSound будут перенесены в мод вместо сгенерированных, генератор нельзя запускать для этого каталога без согласования. Это вопрос процесса в самом моде, ForgeSound его не решает.

**Звук на NixOS** (💭 по устройству пакетов; на железе проверяется на этапе 0, S0-10): `sounddevice` в nixpkgs жёстко указывает путь к `libportaudio` из Nix-store, а PortAudio выводит звук через ALSA. На NixOS с PipeWire это работает при `services.pipewire.alsa.enable = true` (в стандартной конфигурации PipeWire так и есть). Для MVP воспроизведение идёт **в браузере (Web Audio)**, поэтому Python-аудио нужно только для будущего realtime-режима.

Прямой доступ к `freesound.org`, `opengameart.org` и `kenney.nl` из этой сессии закрыт сетевой политикой. | CC-BY-3.0 / CC-BY-4.0 | ✅ Да | Автоматический `CREDITS`: название, автор, ссылка на источник, лицензия и ссылка на её текст, пометка «изменено» для производных |

| Звуки Trailblazer и других локальных проектов | ❌ Нет | Внешняя справочная библиотека «только чтение» (раздел 2.4) |

💭 Отдельно об CC BY-SA: это «копилефт»-лицензия для контента. Она не запрещена принципиально, но требует распространять производные на тех же условиях. Поэтому она отнесена к «по согласованию», а не к «можно».

- Каждый файл хранится неизменным под именем-хешем (`sha256`), а метаданные — внутри библиотеки (раздел 6.8). Атрибуция не теряется при переносе файла и при создании производных звуков.
- Около 20 разнородных материалов (щелчки, затворы, пружины, удары, трубы, реле, фактуры, гул) — без сотен случайных файлов.
- Перед включением каждого кандидата из раздела 3.2 его страницу нужно открыть, а метаданные лучше получить через Freesound API (нужен доступ к `freesound.org` из окружения).

## 4. Три варианта архитектуры

### Как уточнились границы между вариантами

💭 Исследование показало, что настоящий водораздел — **где живёт источник истины о звуке**:
- **A**: источник истины — состояние внешних программ (проект Audacity, патч Surge) плюс скрипт-оркестратор.
- **B и C**: источник истины — собственный граф проекта; внешние программы только рендерят узлы.

B и C поэтому ближе друг к другу, чем кажется: C — это «B плюс адаптеры». Ещё одно уточнение: роль Audacity во всех разумных вариантах минимальна (внешний редактор), потому что в 4.0 убрали scripting pipe. Вариант A «на Audacity» ведёт на тупиковую ветку 3.x.

---

### Вариант A — интеграционная студия

**1. Архитектура и компоненты**

```
 ┌─────────── Веб-UI / PySide6 ───────────┐
 │  список шагов, кнопки, A/B-плеер        │
 └───────────────┬────────────────────────┘
                 │
        ┌────────▼─────────┐  OSC   ┌──────────────────┐
        │ Python-оркестратор├──────►│ Surge XT CLI      │ → аудиоустройство (живой звук)
        │ (сценарии шагов) │        └──────────────────┘
        │                  │ pipe   ┌──────────────────┐
        │                  ├──────►│ Audacity 3.7 GUI  │ ← mod-script-pipe
        │                  │        └──────────────────┘
        │                  │ Python ┌──────────────────┐
        │                  ├──────►│ pedalboard +      │ → оффлайн-рендер Surge XT VST3
        └──────────────────┘        │ Surge XT (VST3)   │
                                    └──────────────────┘
```

**2. Стек.** Python 3.12, `pedalboard`, `python-osc`, `soundfile`, `pyloudnorm`. Audacity 3.7.x из закреплённой ревизии nixpkgs, Surge XT 1.3.4 из nixpkgs.

**3. Интеграция.** Surge: живой звук через OSC в CLI (`/param/...`, `/mnote`), оффлайн — Surge XT VST3 в `pedalboard` (`load_plugin`, состояние через `raw_state`). Audacity: импорт, обрезка, эффекты и экспорт командами pipe.

**4. Огибающие и параметры.** Envelope Tool Audacity (только вручную в GUI; через pipe точки огибающей не задаются удобно 💭) и огибающие Surge (ADSR, MSEG — только в UI Surge или через `.fxp`). Единого таймлайна нет.

**5. ИИ.** LLM формирует последовательность команд pipe и OSC по белому списку. Предложение — это скрипт, а не дифф параметров.

**6. Сэмплы и лицензии.** Каталог файлов плюс CSV с источниками. Происхождение результата фиксируется слабо: что сделано в GUI Audacity, не записывается.

**7. Плюсы и минусы.**
- ➕ Первый звук за 1–2 недели; почти нет своего DSP.
- ➕ Полная мощь Surge и привычный ручной Audacity.
- ➖ **Опора на функцию, которой нет в актуальном Audacity 4.0**; нужен работающий GUI-экземпляр.
- ➖ Нет единого таймлайна, слоёв и огибающих «в одном месте»; рутина переключения между окнами.
- ➖ Воспроизводимость слабая: состояние размазано по трём программам и ручным действиям.
- ➖ ИИ работает «вслепую» через команды; дифф параметров и откат сложны.

**8. Сложность и риски.** Низкая сложность старта, высокие риски поддержки: хрупкий pipe (тайминги, модальные диалоги), разные версии Audacity, синхронизация состояний.

**9. Минимальный прототип.** Скрипт: загрузить WAV в Audacity → обрезать, поднять гейн, сделать фейд → экспорт; отрендерить ноту Surge через `pedalboard` по `.fxp` → смешать в numpy → 3 варианта с разными патчами → A/B в браузере.

**10. Развитие.** Ограничено: при переходе на Audacity 4 без pipe придётся переписывать; рано или поздно появится собственное ядро, то есть фактически вариант C.

### Вариант B — собственная процедурная студия

**1. Архитектура и компоненты**

```
 ┌──────────────────────── UI (TypeScript, canvas/WebGL) ─────────────────────────┐
 │ таймлайн слоёв · дорожки огибающих · спектр · сетка вариантов · панель ИИ        │
 └──────────────┬───────────────────────────────────────────────▲─────────────────┘
                │ ops (JSON)                                    │ буферы/метрики
 ┌──────────────▼───────────────────────────────────────────────┴─────────────────┐
 │ Ядро проекта: граф · журнал операций · undo/redo · ветки-варианты · кэш         │
 ├────────────────────────────────────────────────────────────────────────────────┤
 │ Собственный DSP: сэмплер (trim/speed/pitch/reverse), огибающие (AHDSR, MSEG,   │
 │ переформирование сэмпла), SVF/biquad, шум, модальный резонатор, транзиент-     │
 │ шейпер, сатурация, микшер · Анализ: онсеты, LUFS, спектр, моды, затухание       │
 ├────────────────────────────────────────────────────────────────────────────────┤
 │ ИИ-шлюз (MCP / tool use) · Библиотека с provenance · Экспорт WAV/SNDINFO         │
 └────────────────────────────────────────────────────────────────────────────────┘
   Surge/Audacity — только «открыть файл снаружи» и импорт результата
```

**2. Стек.** Ядро на Rust (`cpal`, `fundsp` или свои узлы, `hound`/`symphonia`, `rubato`, `realfft`, `ebur128`) либо C++. UI: Tauri + TypeScript. DSP-узлы можно писать на Faust и компилировать в Rust.

**3. Интеграция.** Surge — внешний инструмент: рендер в WAV вручную и импорт как ассета. Audacity — внешний редактор через файловый обмен.

**4. Огибающие.** Полностью свои: параметрические (AHDSR с кривизной), многосегментные (как MSEG), переформирование огибающей записанного сэмпла, автоматизация любых параметров узлов на общем таймлайне.

**5. ИИ.** Типизированные операции над графом, анализ, проверка целей (как в C, раздел 6.5).

**6. Сэмплы.** Контентно-адресуемое хранилище с provenance (как в C).

**7. Плюсы и минусы.**
- ➕ Полный контроль над временным дизайном, воспроизводимостью и UX.
- ➕ Детерминированность (свой seed, свои алгоритмы); возможен realtime-движок.
- ➕ Можно выбрать пермиссивную лицензию (MIT/Apache), если не линковать GPL-код.
- ➖ Много собственного DSP. Качество фильтров, дисторшна и резонаторов нужно довести до уровня Surge — это годы чужой работы.
- ➖ Синтез беднее, чем 12 типов осцилляторов и 30+ эффектов Surge «из коробки».
- ➖ Rust + Tauri + свой DSP — самый долгий путь до первого «хорошо звучащего» результата.

**8. Сложность и риски.** Высокая. Главный риск — потратить месяцы на DSP-инфраструктуру и проиграть по звуку готовым решениям; второй — realtime на Rust с первого дня.

**9. Минимальный прототип.** Сэмплер, AHD-огибающая, SVF, шум, микшер, 3 варианта, экспорт; UI с одним таймлайном.

**10. Развитие.** Свой плагин (CLAP через `nih-plug`, ISC), Faust-узлы, WASM-версия в браузере.

```
 ├────────────────────────────────┴───────────────────────┴───────────────────────┤
 │ ИИ-шлюз: MCP-сервер / tool use — только типизированные операции и анализ       │
 │ Библиотека: контентно-адресуемые ассеты + provenance + политика лицензий       │
 │ Экспорт: WAV (16/24 бит), манифест, SNDINFO-фрагмент, CREDITS                   │
 │ Внешний редактор: Audacity (файловый обмен, новая ревизия ассета)              │
 └────────────────────────────────────────────────────────────────────────────────┘
```

**2. Стек.**
- Ядро и движок: **Python 3.13** (nixos-26.05) + numpy, scipy, soundfile; громкость и признаки — собственный код (pyloudnorm и librosa не нужны); **surgepy** (сборка из исходников Surge в Nix-деривации, отдельный процесс); **pedalboard** — не в MVP (нет в nixpkgs, раздел 6.11); Signalsmith Stretch через небольшую обёртку или Rubber Band.
- API: FastAPI + WebSocket (локальный сервер, слушает только `127.0.0.1`).
- UI: TypeScript + Svelte (или React) + canvas; на старте wavesurfer.js для волны и регионов. Воспроизведение — Web Audio API: `AudioBuffer` из присланного PCM, мгновенное A/B-переключение с выравниванием громкости. Позже — упаковка в Tauri.
- Окружение: Nix flake (devShell + деривация `surgepy` с закреплённым коммитом Surge).
- 💭 Почему Python, а не Rust: `surgepy` — нативный Python-API Surge; render-on-edit для коротких звуков не требует realtime-ядра; самый быстрый путь проверить главную гипотезу «удобно делать качественные короткие звуки». Узкие места потом переносятся в Rust или Faust за неизменным интерфейсом узла.

**3. Интеграция с Surge XT и Audacity.**
- **Surge-узел (основной путь):** воркер-процесс с `surgepy`. Узел хранит ссылку на базовый патч (`.fxp` в хранилище по хешу), **курированный набор параметров** с понятными именами («osc1.type», «filter1.cutoff», «amp_eg.decay»…), MSEG-огибающие и ноту/высоту/длительность гейта. Рендер: `createSurge(sr)` → `loadPatch` → `setParamVal`/`setMSEG` → `playNote` → `processMultiBlock` → `releaseNote` → хвост до порога тишины.
- **Surge как процессор сэмплов:** `processMultiBlockWithInput` (осциллятор или эффект Audio Input). ✅ Работает в пробном прогоне этапа 0 (S0-5). Вариант «Surge XT Effects VST3 через `pedalboard`» отложен: `pedalboard` нет в nixpkgs (раздел 6.11).
- **Live-режим (позже):** Surge XT standalone/CLI по OSC для «покрутить ручки». Финальный рендер всё равно идёт через `surgepy`.
- **Изоляция:** Surge работает в отдельном процессе. Падение или зависание не роняет ядро, а GPL-граница чётко очерчена (хотя проект и так под GPL, раздел 6.10).
- **Audacity:** только «Открыть во внешнем редакторе» с файловым обменом (раздел 2.2). Pipe не используется.

**4. Огибающие и параметры.** Свои огибающие и автоматизация на общем таймлайне (раздел 6.4). Для Surge-узла огибающие таймлайна транслируются в MSEG или в параметры ADSR, а для параметров без MSEG — в поблочную автоматизацию `setParamVal` между блоками рендера (✅ размер блока задаётся при компиляции, `SURGE_COMPILE_BLOCK_SIZE`, обычно 32 сэмпла, ≈ 0,7 мс при 48 кГц; 💭 достаточность такого разрешения проверить).

**5. ИИ.** MCP-сервер или tool use с операциями над графом, анализом и проверкой целей. Предложения ИИ — ветки-changeset'ы с объяснением; пользователь принимает их целиком, частично или отклоняет (раздел 6.5).

**6. Сэмплы и лицензии.** Контентно-адресуемая библиотека, сайдкары происхождения, импорт через Freesound API, политика лицензий при экспорте, автогенерация `CREDITS` (раздел 6.8).

**7. Плюсы и минусы.**
- ➕ Качество звука Surge доступно с первого дня, свой DSP нужен только там, где Surge неудобен (сэмплер, огибающие сэмплов, модальный резонатор, анализ).
- ➕ Полный контроль над временным дизайном и воспроизводимостью: граф и журнал операций принадлежат проекту.
- ➕ ИИ и человек работают через один и тот же набор операций.
- ➕ Модульность: узел Surge можно заменить узлом Faust/Rust без изменения проекта.
- ➖ Связь с GPL-кодом делает проект GPL-3.0-or-later.
- ➖ Сборка `surgepy` в Nix и закрепление версий — инженерная работа на старте.
- ➖ Python-движок ограничивает realtime-сценарии (компенсируется render-on-edit).

**8. Сложность и риски.** Средняя. Риски: детерминизм Surge; скорость рендера при массовой генерации вариаций; стабильность API `surgepy`; хостинг VST3 на NixOS. Все проверяются на этапе 0 (раздел 7).

**9. Минимальный прототип.** Загрузка сэмпла → цепочка (trim, speed/pitch, огибающая, фильтр) → дополнительный слой (шум и/или Surge-нота и/или второй сэмпл) → правка огибающих мышью → 3–8 вариаций → A/B с выравниванием громкости → экспорт WAV и манифеста.

**10. Развитие.** Real-time preview (раздел 6.12); Surge standalone/OSC; перенос узлов в Rust/Faust; хостинг CLAP; пакетный «рецепт-генератор» для серии звуков одного стиля; экспорт пакетов для UZDoom/GZDoom.

## 6. Подробная архитектура рекомендуемого решения

### 6.1 Основные понятия

| Понятие | Определение |
|---|---|
| **Asset** | Неизменяемый аудиофайл в хранилище (`sha256`), с сайдкаром происхождения |
| **Layer** | Слой на таймлайне: источник (Asset-клип, Surge-нота, шум, резонатор) + цепочка узлов + огибающие + позиция во времени |
| **Node** | Узел обработки с типизированной схемой параметров (JSON Schema) и версией реализации |
| **Lane** | Дорожка автоматизации параметра (огибающая) на общей шкале времени |
| **Revision** | Неизменяемое состояние графа (хеш); операции переводят одну ревизию в другую |
| **Variant** | Именованная ветка от ревизии: набор параметрических отличий + seed |
| **Proposal** | Предложение (ИИ или «генератор»): changeset операций + объяснение + цели |
| **Render** | Результат рендера ревизии или варианта: PCM + метрики; кэшируется по хешу |

### 6.2 Формат проекта

Проект — каталог (удобен для git), например `hitmarker_industrial.forge/`:

```
hitmarker_industrial.forge/
  project.json            # текущий граф (HEAD), schemaVersion, sampleRate, длительность
  history/
    ops.jsonl             # журнал операций (append-only), автор: human|ai|generator
    revisions/<hash>.json # снимки графа (периодически и на ветвлениях)
  variants.json           # ветки-варианты и их seed
  proposals/<id>.json     # предложения ИИ (принятые/отклонённые/ожидающие)
  assets -> ../library    # ссылка на общую библиотеку ИЛИ локальная копия
  cache/renders/<hash>.f32  # кэш рендеров (не коммитится)
  exports/<name>/         # WAV + export-manifest.json
```

### 6.3 Операции, история, отмена, изоляция

**Операция** — минимальное типизированное изменение графа:

```json
{ "op": "set_param", "target": "layers/click/chain/click.eq/params/bands/0/gain_db",
  "value": -12, "prev": -9, "author": "human", "ts": "2026-10-29T12:00:00Z" }
```

Набор операций (схемы публикуются для UI и ИИ):
`add_layer`, `remove_layer`, `move_layer(start_ms)`, `set_source`, `trim_source(in_ms,out_ms)`, `add_node`, `remove_node`, `reorder_node`, `set_param`, `set_lane_points`, `insert_lane_point`, `set_curve`, `align_layers(by=onset)`, `create_variant`, `set_variant_spec`, `rename`, `bake_external_edit(asset, parent_asset)`.

- **Undo/redo:** у каждой операции есть `prev`, поэтому обратная операция строится автоматически. Группы операций (жест мышью, предложение ИИ) образуют транзакцию.
- **Ветки:** вариант или предложение — ветка от ревизии; слияние означает применение changeset'а к HEAD с проверкой конфликтов по путям.
- **Воспроизводимость:** ревизия плюс версии движков (`engine`) плюс seed однозначно определяют результат. Тест: «рендер ревизии X дважды → одинаковый хеш PCM» (или расхождение ≤ −120 dBFS, если бит-в-бит недостижимо).
- **Классы воспроизводимости узлов** (новое в версии 2, из-за случайности Surge, раздел 2.1):

  | Класс | Что гарантирует | Примеры |
  |---|---|---|
  | `exact` | Бит-в-бит при тех же версиях | Свои узлы ядра (seed из проекта), детерминированные конфигурации Surge |
  | `seeded` | Бит-в-бит после доработки: seed передаётся движку | Surge с небольшим патчем в нашей Nix-деривации, который открывает `seed` для `RNGGen`/`noiseRng`/`random_device`-источников. 💭 Патч стоит предложить и в upstream Surge |
  | `frozen` | Результат запоминается при первом рендере (контентный хеш) и дальше берётся из «заморозки»; в проекте отмечено «недетерминированный источник» | Surge-конфигурации со случайностью до появления `seeded`; внешние плагины |

  Класс узла определяется автоматически (двойной рендер при первом использовании конфигурации) и виден пользователю. Экспорт из `frozen` всегда воспроизводим, потому что использует замороженный буфер; повторный рендер с нуля может отличаться, и UI об этом предупреждает.
- **Изоляция от оригиналов:** ассеты неизменяемы и адресуются хешем; операции никогда не пишут в них. Обработанное — только рендеры и экспорт.

### 6.4 Временной дизайн

#### Что показывать на общем таймлайне

| Элемент | Представление |
|---|---|
| Слои | Горизонтальные дорожки-клипы с волной; перетаскивание = `start_ms`; ручки trim in/out и фейдов |
| Огибающая громкости слоя (amp) | Линия поверх волны клипа, точки и кривизна сегментов. Исходная огибающая сэмпла показана «призраком» |
| Огибающая высоты (pitch) | Сворачиваемая дорожка под слоем, полутоны |
| Фильтр: cutoff и resonance | Сворачиваемые дорожки под слоем (log-шкала частоты) |
| Маркеры | Онсет (детектированный пик атаки), конец атаки, начало хвоста, точка −60 дБ |
| Мастер | Суммарная волна, мастер-гейн, суммарная огибающая |
| Сетка | Миллисекунды; пресеты масштаба: 0–20 мс (атака), 0–200 мс, 0–1 с |

#### Что выносить в отдельные редакторы

- **Спектр и спектрограмма** слоя или микса: маркеры резонансов (частота, добротность, время затухания), сравнение «до/после».
- **Кривая EQ и фильтров:** частотная характеристика с перетаскиваемыми полосами.
- **Модальный резонатор:** таблица мод (частота, амплитуда, затухание) с импортом «моды из сэмпла».
- **Панель Surge-узла:** курированные параметры, выбор осциллятора и фильтра, MSEG-редактор.
- **Сетка вариантов** (раздел 6.6).

#### Модели огибающих (не только ADSR)

1. **Параметрическая AHDSR + кривизна** — для синтетических слоёв. Для one-shot звуков sustain и release задаются через «длительность гейта» (`gate_ms`): нажатия и отпускания ноты нет.
2. **Многосегментная (breakpoints/MSEG)** — точки `(t_ms, value)` с кривизной каждого сегмента. Совместима с MSEG Surge по структуре сегментов (duration, v0, control point).
3. **Переформирование огибающей записанного сэмпла.** Анализатор извлекает исходную огибающую (RMS или пиковый follower с атакой ≈ 0,1 мс и релизом ≈ 5 мс) и предлагает сегментацию: *транзиент → тело → хвост*. Пользователь двигает границы и уровни сегментов, а ядро вычисляет коэффициент усиления `target(t) / original(t)` (с ограничением и сглаживанием). Так меняется форма записи, а не накладывается вторая огибающая «сверху».
4. **Разделение транзиент/сустейн** (transient shaper): отдельные регуляторы атаки и тела — самый частый инструмент для hitmarker'ов.
5. **Сегментное растяжение времени:** растянуть или сжать только хвост (Signalsmith Stretch), оставив транзиент нетронутым. Альтернатива для механики — varispeed только хвоста.
6. **Затухание по полосам:** укоротить хвост только выше N кГц («убрать кристальный звон»), не трогая низ и середину. Реализуется многополосной огибающей (кроссовер плюс огибающие полос).

#### Синхронизация слоёв

- Выравнивание по **онсету**, а не по началу файла (`align_layers(by=onset)`): у записей разная «тишина до удара».
- Субмиллисекундный сдвиг (шаг 0,02 мс), инверсия полярности и проверка фазовой когерентности низа при сложении (индикатор «потери» энергии в полосе 40–200 Гц).
- Группы слоёв с общим смещением.

### 6.5 Взаимодействие с ИИ

| | ИИ-разработчик | ИИ внутри студии |

```
                ┌────────────▼────────────┐
                │ forge-mcp: инструменты   │  ← стабильный контракт:
                │ = операции + анализ      │    JSON Schema операций,
                └────────────┬────────────┘    версия схемы
                             │
                        Ядро ForgeSound
```

- **Стабильный контракт — схема операций и MCP-инструменты**, а не API конкретной модели. Любой MCP-клиент управляет студией одинаково. Уже на этапе 5 им может быть сам Claude Code, без встроенной ИИ-панели.
- Встроенная ИИ-панель (позже) общается с моделью через адаптер с узким интерфейсом `complete(messages, tools) → tool_calls/text`. Адаптеры: Anthropic API, «OpenAI-совместимый» HTTP (покрывает большинство локальных серверов). Ключи хранятся локально; без настроенного провайдера панель просто выключена.
- 💭 Локальные модели заметно слабее в многошаговом tool use. Схема операций поэтому проектируется так, чтобы ей могла пользоваться и небольшая модель: плоские параметры, явные единицы, короткие описания, валидация с понятными ошибками.
- Облачная модель — опция пользователя, а не зависимость: никаких облачных сервисов ForgeSound не требует.

**Интерфейс:** MCP-сервер, запущенный ядром (локально). Инструменты:

| Инструмент | Назначение |
|---|---|
| `get_project` | Граф HEAD, краткое описание слоёв и узлов |
| `list_node_types` | Схемы узлов и параметров с диапазонами и единицами |
| `analyze(target)` | Признаки ассета, слоя или рендера: время атаки (10→90 %), пик, crest factor, короткая громкость, спектральный центроид, время до −20/−40/−60 дБ общее и по полосам, найденные резонансы (f, Q, T60), длительность |
| `propose(ops, rationale, goals)` | Создать ветку-предложение. `goals` — измеримые цели |
| `render(variant\|proposal)` | Рендер и метрики, проверка целей |
| `compare(a, b)` | Разница метрик |

ИИ **не получает** доступа к файловой системе и shell. Каждый вызов — это операция, которую можно увидеть, отменить и повторить.

**Пример запроса:** «Создай индустриальный hitmarker из этого металлического щелчка. Сохрани резкую атаку, добавь немного веса, убери кристальный звон и сократи хвост. Сделай три разных варианта».

1. ИИ вызывает `analyze(asset)` и получает, например: атаку 0,4 мс; резонанс 6,8 кГц, Q≈40, T60 = 380 мс; хвост до −60 дБ за 520 мс.
2. ИИ формирует **цели**:
   - `attack_ms ≤ 0.6`;
   - `resonance(6.8 kHz).T60 ≤ 80 ms` или `level ≤ −12 dB`;
   - `tail_to_-60dB ≤ 220 ms`;
   - `energy(60–250 Hz) ≥ +4 dB` относительно исходника.
3. ИИ создаёт 3 предложения с разными «рецептами»:
   - **V1 «Плотный»:** динамический notch 6,8 кГц, многополосное сокращение затухания выше 4 кГц; Surge-слой: синус с pitch-envelope 7→0 полутонов за 25 мс плюс сатурация.
   - **V2 «Индустриальный»:** понижение исходника на 3 полутона (varispeed); слой фильтрованного шума (полоса 1–3 кГц, 40 мс); Combulator/Resonator Surge с низкой добротностью; транзиент-шейпер +3 дБ.
   - **V3 «Сухой механизм»:** нарезка только транзиента (12 мс) плюс модальный резонатор с модами из `metal pipe 01` (короткий T60); низ — короткий thump из Kenney `impactMetal_heavy`.
4. Ядро рендерит, проверяет цели и показывает каждому варианту: ✅/❌ по целям, дифф параметров, объяснение и A/B с выравненной громкостью.
5. Пользователь принимает V2 целиком, а из V1 переносит только notch, затем правит огибающую мышью — это те же операции, только с `author: human`.

**Сопоставление слов и признаков** (стартовый словарь, 💭 уточняется на практике):

| Формулировка | Измеримый признак | Типичные операции |
|---|---|---|
| «резкая атака» | attack 10→90 % < 1 мс, crest factor | Транзиент-шейпер, обрезка преатаки, ВЧ-клик |
| «вес» | Энергия 50–250 Гц, длительность низа | Слой «thump» (синус + pitch env), понижение тона, сатурация |
| «кристальный звон» | Узкие пики > 3 кГц с длинным T60 | Notch, динамический EQ, многополосное затухание |
| «короче хвост» | Время до −60 дБ | Огибающая хвоста, гейт, затухание по полосам |
| «индустриальный» | Шумовая составляющая, неоднородность спектра | Шумовые и фактурные слои, ring mod, дисторшн |

### 6.6 Вариации и сравнение

**Спецификация вариаций** (`variant_spec`): для параметров задаются диапазоны и распределения, для других — блокировки:

```json
{ "seed": 1337, "count": 64, "select": 6,
  "vary": { "layers/weight/source/params/amp_eg.decay": { "range": [0.2, 0.45] },
            "layers/click/chain/click.pitch/params/semitones": { "range": [-5, 0], "step": 0.5 },
            "layers/*/start_ms": { "jitter": 0.6 } },
  "lock":  [ "goals.attack_ms" ],
  "structural": [ "swap_source(click, pool:latch_clicks)" ] }
```

- **Генерация:** N кандидатов с детерминированным seed (`numpy.random.Generator(PCG64(seed))`). Каждый кандидат хранится как дельта параметров, а не как WAV.
- **«Существенно различающиеся»:** у кандидатов вычисляются вектора признаков (MFCC-статистики, центроид, затухание по полосам, атака, длительность), затем farthest-point sampling выбирает k максимально удалённых. Кандидаты, нарушающие цели, отбрасываются.
- **Структурные вариации:** замена источника из пула, другой тип осциллятора Surge, включение и выключение слоя.
- **Микровариации для игры:** небольшие случайные отличия (±0,5 полутона, ±0,3 мс между слоями) для `$random` в SNDINFO, чтобы повторяющийся hitmarker не утомлял.

**Сравнение:**
- Сетка карточек: волна, мини-спектр, длительность до −60 дБ, атака, короткая громкость, статус целей.
- **Выравнивание громкости при прослушивании:** 💭 integrated LUFS для звуков < 400 мс ненадёжен. Метрики ядра: (1) **`a_rms_50ms`** — A-взвешенный RMS самых громких 50 мс, ✅ та же мера, которой Trailblazer калибрует свои звуки (`f10_hitsounds.a_rms`); (2) максимум K-взвешенного RMS в окне 50 мс; (3) пик и true-peak. Выравнивание при A/B — **только на время прослушивания**: в проект и экспорт оно не записывается.
- **Громкость не уравнивается «для всех»** (требование версии 2). Цель громкости задаёт профиль экспорта: в профиле Trailblazer — громкость **текущего файла с тем же именем** (сохраняет баланс, принятый на слух) или явное смещение в дБ, заданное пользователем. Кроме того, в профиле учитывается, что пользователь может убавить звук ползунком `tb_hitsound_vol` (0,05…1,0): поэтому звук должен оставаться различимым и на пониженной громкости (проверка маскировки на −6 и −12 дБ).
- **Контекстное прослушивание:** фоновая петля выстрелов с регулируемым уровнем — CC0 The Free Firearm Sound Library в распространяемой версии, **реальные выстрелы мода** из локальной копии Trailblazer в профиле Trailblazer. Плюс метрика маскировки по методу `f10_gunmask.py`: третьоктавные полосы первых 100 мс, лучшая полоса над выстрелом (медиана / худший ствол).
- Слепой A/B/X-режим: варианты перемешиваются, имена скрыты.

### 6.7 Предпрослушивание без экспорта

- Каждая операция инвалидирует кэш затронутых узлов (ключ кэша — хеш параметров подграфа плюс версии движков).
- Перерендер затронутых слоёв и микс в память (float32) → отправка в UI по WebSocket → Web Audio. 💭 Ожидаемо 5–50 мс для звука 0,5 с с 3–4 слоями на numpy. Surge-узел медленнее (создание экземпляра, загрузка патча), поэтому воркеры держат «тёплые» экземпляры Surge с загруженным патчем. Фактическое время Surge-рендера измеряет этап 0 (S0-4).
- Цель латентности «отпустил мышь → слышу результат»: ≤ 100 мс (критерий этапа 2).
- Режимы прослушивания, планировщик и защита от устаревших результатов — раздел 6.12.

### 6.8 Библиотека сэмплов и происхождение

```
library/
  objects/sha256/9f/2c…/audio.wav     # оригинал, байт-в-байт
  objects/sha256/9f/2c…/asset.json    # провенанс (ниже)
  index.sqlite                        # поиск по тегам/признакам (производный, пересобирается)
```

`asset.json`:

```json
{
  "sha256": "9f2c…", "kind": "original",
  "source": { "site": "freesound", "id": 397595,
              "url": "https://freesound.org/people/Nightflame/sounds/397595/",
              "title": "Latch Clicks 2", "author": "Nightflame",
              "retrieved_at": "2026-11-02T10:00:00Z", "via": "freesound-api-v2" },
  "license": { "spdx": "CC0-1.0", "url": "https://creativecommons.org/publicdomain/zero/1.0/",
               "snapshot": "license-snapshots/…", "attribution_required": false,
               "commercial_ok": true },
  "audio": { "format": "wav", "sample_rate": 44100, "bit_depth": 16, "channels": 2, "duration_s": 0.0 },
  "tags": ["metal", "latch", "click"], "notes": "",
  "derived_from": null
}
```

- Внешне отредактированный ассет (Audacity) получает `kind: "derived"`, `derived_from: <sha256>` и `tool: "audacity 3.7.x"`.
- **Политика при экспорте:** обход всех ассетов-предков рендера. `CC0` → без условий; `CC-BY-*` → автогенерация `CREDITS` и блока атрибуции в манифесте; `*-NC-*`, `*-ND-*`, `*-SA-*`, «неясно» → блокировка экспорта в профиле «распространяемый» с объяснением, пока владелец не согласовал исключение (оно записывается в `license.exception` с датой и причиной).
- **Импорт:** через Freesound API (метаданные и лицензия автоматически); ручной импорт локальных файлов требует обязательного заполнения полей лицензии.

#### Импорт любых форматов (версия 2)

- Тип файла определяется **по сигнатуре** (`RIFF`, `OggS`, `fLaC`, `ID3`/MPEG-кадр, Doom DMX `03 00`), расширение не учитывается.
- Декодеры по порядку: libsndfile (WAV, FLAC, Ogg Vorbis/Opus, MP3 — версия 1.2.2 в nixos-26.05), собственный декодер Doom DMX (20 строк), ffmpeg как запасной путь.
- Оригинал сохраняется **байт-в-байт в исходном формате**; рабочее представление — float32 в памяти, а рабочий и экспортный формат — WAV. ✅ Проверено на всех 455 звуках Trailblazer (раздел 2.4).
- 💭 Сжатые с потерями исходники (OGG, MP3) помечаются в метаданных: их артефакты в верхних частотах заметны при сильной обработке.

#### Метаданные не теряются при переносе и в производных

1. **Внутри библиотеки:** `asset.json` рядом с объектом, а не в отдельной базе. `index.sqlite` — только производный индекс, его можно удалить и пересобрать.
2. **В проекте:** проект ссылается на ассеты по `sha256` и при экспорте собирает их полные `asset.json` в `export-manifest.json`. Перенос проекта на другую машину вместе с объектами сохраняет и атрибуцию.
3. **В производных звуках:** каждый экспортированный WAV получает запись `derived_from` (все предки с лицензиями) в манифесте. 💭 Встраивать атрибуцию **внутрь WAV** (RIFF `LIST/INFO`: `IART`, `ICOP`, `ICMT`) — опция профиля. В профиле Trailblazer она по умолчанию выключена, пока не проверено, что UZDoom корректно читает WAV с дополнительными чанками (проверка этапа 7).
4. **`CREDITS`:** генерируется при каждом экспорте из манифеста — по строке на ассет: название, автор, ссылка, лицензия и ссылка на её текст, «изменено: да». Формат совместим с тем, как Trailblazer пишет атрибуцию (комментарии в `SNDINFO.txt`), поэтому генерируется ещё и готовый комментарий для SNDINFO.

#### Внешние справочные библиотеки (только чтение)

Папку чужого проекта (например, `Trailblazer-Extended/src/Sounds`) можно подключить как справочную библиотеку: ForgeSound индексирует файлы на месте (хеш, формат, громкость), **не копирует их в свою библиотеку и никогда не пишет в эту папку**. Лицензия таких файлов — «локальная, не для распространения»; производные наследуют эту пометку.

### 6.9 Экспорт и интеграция с модами

Общее для всех профилей:
- Рабочий и экспортный формат — **WAV** (PCM 16/24 бит или float32); частота и каналы задаёт профиль. Детерминированный экспорт: полифазный ресэмплинг и TPDF-дизеринг с фиксированным seed (✅ проверяется в S0-9).
- `export-manifest.json`: ревизия, вариант, seed, класс воспроизводимости, версии движков, метрики, все ассеты-предки с лицензиями. Этого достаточно, чтобы воспроизвести WAV из проекта.
- **Экспорт только в отдельный каталог** (по умолчанию `<проект>.forge/exports/<профиль>/<дата-время>/`). Запись в каталоги, зарегистрированные как «чужой проект», запрещена кодом (раздел 6.13).

#### Профиль «Trailblazer» (на основе аудита, раздел 2.4)

Профиль ничего не меняет в моде: он **читает** локальную копию мода (путь задаёт пользователь) и **пишет** только в каталог экспорта ForgeSound. Перенос файлов в мод делает владелец сам или отдельной, согласованной задачей в репозитории мода.

**Режимы:**

| Режим | Что получается | Изменения в моде |
|---|---|---|
| **A. Замена стиля** (по умолчанию) | Полный комплект файлов **с существующими именами** выбранного стиля, например `TBHITMEA.wav` + `TBKMEA1…5.wav` | Нет. SNDINFO не трогается: достаточно заменить 6 файлов |
| **B. Отдельные звуки** | Новые ламп-имена (≤ 8 символов, уникальные) + готовый фрагмент `SNDINFO` с логическими именами и, при желании, `$random`/`$volume` + комментарий-атрибуция | Нужна строка в SNDINFO; без кода |
| **C. Новый (седьмой) стиль** | Файлы + фрагмент SNDINFO + **текстовое описание** нужных изменений: `STYLE_SND`, `clamp(style, 0, 5)`, CVar, меню, LANGUAGE | Да, затрагивает код мода. ForgeSound только описывает изменения; вносить их — отдельная задача в моде по согласованию владельца (по правилам `CLAUDE.md` мода) |

**Структура экспорта (режим A):**

```
exports/trailblazer/2026-11-05T14-03-22_meat-v2/
  Sounds/TBHITMEA.wav  Sounds/TBKMEA1.wav … Sounds/TBKMEA5.wav   # раскладка как в src/
  SNDINFO.fragment.txt        # пусто в режиме A (только комментарий-атрибуция)
  CREDITS.md                  # атрибуция всех предков
  export-manifest.json        # ревизии, seed, версии, метрики, лицензии
  trailblazer-report.md       # результат проверок (ниже), сравнение с текущими файлами мода
```

**Проверки профиля** (каждая — PASS/WARN/FAIL с объяснением; при FAIL экспорт не помечается как готовый):

| # | Проверка | Правило (из кода и файлов мода) |
|---|---|---|
| T1 | Имена | Ламп-имя = имя файла без расширения, ≤ 8 символов, `A–Z 0–9 _`; в режиме A — точное совпадение с существующим именем; в режиме B — нет совпадений с **любым** ламп-именем в `src/` мода (движку неважен каталог) |
| T2 | Регистрация | Режим A: имя присутствует в `SNDINFO.txt` и привязано к ожидаемому логическому имени (`tb/hit/<style>`, `tb/kill/<style>N`). Режим B: в сгенерированном фрагменте нет конфликтов с логическими именами SNDINFO |
| T3 | Комплектность | Для стиля: 1 попадание + 5 ступеней убийства; для одиночных звуков — всё, что перечислено в проекте |
| T4 | Формат | WAV PCM 16 бит, моно, 44 100 Гц (как все 36 текущих файлов F-10), без DC, без клиппинга, пик ≤ −0,4 дБFS (0,95, как в генераторе) |
| T5 | Длительность | Попадание ≤ 0,15 с, убийство ≤ 1,0 с (WARN, а не FAIL: текущие 0,075–0,11 и 0,62–0,75 с); короткий фейд-аут в конце |
| T6 | Громкость | `a_rms_50ms` относительно **текущего файла того же имени** в моде; по умолчанию допуск ±1 дБ; убийство относительно попадания своего стиля: +3 дБ ± 1 (как в калибровке владельца). Любую цель можно переопределить в проекте явным смещением |
| T7 | Различимость | Метод `f10_gunmask.py`: третьоктавные полосы первых 100 мс против первых выстрелов 20 видов оружия мода; ориентир — медиана ≥ +4 дБ, худший ствол ≥ 0 дБ; дополнительно на −6 и −12 дБ (пониженный `tb_hitsound_vol`) |
| T8 | Высота в игре | Попадание прослушивается и анализируется на −4,5 / 0 / +3 полутона (`HitPitch`): ни на одной высоте T7 не должна падать ниже 0 дБ у худшего ствола |
| T9 | Ступени серии | Ступени 1…5 различимы между собой (сдвиг основного тона или центроида), но громкость одинакова в пределах ±1 дБ |
| T10 | Лицензии | Все предки — CC0/CC BY или согласованные исключения; производные от звуков самого мода помечены «только для мода» |

**Прослушивание в профиле:** кнопки «Попадание (слабый / средний / сильный урон)» — три высоты из `HitPitch`; «Серия» — повтор логики «Тестовой серии» мода (два попадания, затем убийства x1…x5 с теми же паузами в тиках: 7, 9, 13, 12, 12, 12 тиков по 1/35 с); «Поверх выстрела» — выбор оружия мода.

**Проверка в игре (этап 7, по желанию владельца):** временная копия мода с файлами экспорта, запуск UZDoom 5 и запись звука игры через WAV-драйвер OpenAL Soft (`docs/TESTING.md` §1c мода), затем сравнение записанного с ожидаемым. Копия создаётся во временном каталоге ForgeSound; сам репозиторий мода не меняется.

### 6.12 Режимы прослушивания и планировщик рендера (версия 2)

#### Два режима

| Режим | Поведение | Когда |
|---|---|---|
| **Render-on-change** | Изменение (отпускание мыши, ввод значения, принятое предложение ИИ) → один перерендер → звук обновлён | MVP, по умолчанию |
| **Real-time preview** | Звук обновляется во время изменения | После MVP, переключатель в UI |

Real-time preview вводится **ступенями**, и каждая ступень не требует переписывать движок:

1. **Live re-render** (сразу после MVP): во время перетаскивания рендеры запускаются с ограничением частоты (например, не чаще раза в 40 мс, выигрывает последний), а one-shot проигрывается в петле с авто-повтором. Для звуков в 0,1–0,7 с это субъективно и есть «реальное время», если рендер укладывается в ~30 мс.
2. **Потоковый движок**: тот же граф исполняется блоками в аудио-колбэке; параметры меняются прямо во время звучания (сглаживание параметров). Сначала в Python-процессе с `sounddevice` для лёгких графов, затем — перенос узлов в Rust/Faust за тем же контрактом.
3. **Surge в realtime**: воркер получает параметры по каналу сообщений между блоками либо используется Surge XT standalone через OSC (для «покрутить ручки»), а финальный рендер всё равно идёт оффлайн.

#### Что закладывается в MVP, чтобы не переписывать движок

- **Потоковый контракт узла с первого дня:**
  `prepare(sr, max_block) → state`, `process(state, inputs, n_frames, params_at_block) → outputs`, `reset(state)`.
  Оффлайн-рендер — тот же цикл с большим блоком (весь звук за 1–4 вызова), realtime — с маленьким (64–256 сэмплов). Параметры передаются как кривые автоматизации, сэмплируемые на блок, а не как константы.
- **Узлы делятся на `streaming` и `offline-only`.** Offline-only — нормализация «по всему файлу», реверс, time-stretch целого клипа, анализ. В realtime-режиме их результат заранее «замораживается», а на графе это видно значком.
- **Без скрытого состояния вне `state`**: иначе один и тот же граф по-разному звучит оффлайн и в realtime.
- **Тест эквивалентности** (с этапа 1): рендер блоками по 64 и одним блоком дают одинаковый результат (≤ −120 дБ) для всех `streaming`-узлов.

#### Планировщик и защита от устаревших результатов

- Каждое изменение проекта увеличивает **номер ревизии** `rev`. Задание рендера несёт `(rev, graph_hash)`.
- **Правило «новое побеждает»:** результат применяется к UI, только если его `rev` — самая новая из запрошенных и `graph_hash` совпадает с текущим графом. Опоздавший результат старой ревизии не перезаписывает новую — он только попадает в кэш (вдруг пользователь отменит изменение).
- **Отмена:** запуск новой ревизии отменяет ещё не начатые задания старых; уже идущий рендер Surge доводится до конца, но его результат проходит через то же правило.
- **Состояние видно всегда** — индикатор у плеера и у каждого слоя:

  | Состояние | Значок | Что значит |
  |---|---|---|
  | Актуально | ● зелёный | Слышите ревизию `rev N`, она совпадает с проектом |
  | Рендер | ◐ анимация + «rev N, 34 мс» | Идёт пересчёт; пока звучит предыдущая версия (с пометкой) |
  | Устарело | ● жёлтый | Проект изменился, рендер ещё не запускался (например, Surge-воркер занят) |
  | Ошибка | ● красный + текст | Рендер не удался (ошибка узла, упавший воркер); звучит последняя удачная версия с пометкой |

- **Падение воркера** не роняет ядро: воркер перезапускается, задание повторяется один раз, затем — состояние «Ошибка» (проверяется в S0-6).
- В этапе 0 правило «новое побеждает» проверяется модульно (S0-7); в этапе 1 — на настоящем планировщике с искусственными задержками рендера.

### 6.13 Защита существующих проектов (версия 2)

- **ForgeSound — отдельный репозиторий** (`Kostr2007/ForgeSound-Engine`). Код, документы, библиотека и проекты ForgeSound не смешиваются с исходниками Trailblazer.
- **Trailblazer подключается как «внешний проект» по пути только для чтения.** Профиль хранит путь к корню мода, а ядро проверяет перед любой записью: целевой путь не находится внутри зарегистрированного внешнего проекта (сравнение реальных путей после `realpath`, с учётом симлинков). Нарушение — ошибка, а не предупреждение.
- Файлы мода открываются только на чтение; индексы и кэши по ним хранятся в каталоге ForgeSound.
- Генератор `f10_hitsounds.py` не переписывается и не вызывается для каталога мода. ForgeSound может *прочитать* его результаты как референсы.
- Процесс разработки: в рамках ForgeSound никакие коммиты в ветки Trailblazer не делаются. Изменения мода (например, седьмой стиль, режим C) — только отдельной задачей в репозитории мода после согласования владельца.
- В этой сессии репозиторий Trailblazer склонирован **только для чтения**, в отдельный каталог вне ForgeSound; никаких изменений и коммитов в нём нет.

### Этап 2 — UI MVP: таймлайн и огибающие (3–4 недели)

- **Цель:** удобная ручная работа мышью.

### Этап 3 — Синтезированные слои и звуковые инструменты (3–4 недели)

- **Цель:** качество звука, сопоставимое с ручной работой в DAW.
- **Функции:** Surge-узел (воркер, курированные ~30 параметров, MSEG из таймлайна, пресет-патчи «thump», «metal ping», «noise burst»); модальный резонатор с импортом мод из сэмпла; транзиент-шейпер; сатурация; многополосное затухание; переформирование огибающей сэмпла (транзиент/тело/хвост); выравнивание слоёв по онсету; спектральный вид с маркерами резонансов.
- **Результат:** 5 эталонных звуков (hitmarker ×3, kill confirm ×2), сделанных полностью в ForgeSound.
- **Критерии готовности:** все 5 звуков проходят экспертную оценку автора проекта не хуже референсов, сделанных вручную в DAW; изменение огибающей Surge-слоя на таймлайне слышно и воспроизводимо.
- **Проверка:** слепое сравнение с референсами; golden-тесты Surge-узла (если этап 0 подтвердил детерминизм).
- **Риски:** соответствие огибающих таймлайна и MSEG; падения воркера (решается изоляцией процесса и таймаутами).

### Этап 4 — Вариации и сравнение (2–3 недели)

- **Цель:** быстро получать и выбирать существенно разные варианты.
- **Функции:** `variant_spec`, детерминированная генерация N кандидатов, отбор k наиболее различающихся, структурные вариации из пулов; сетка карточек с метриками; выравнивание громкости при прослушивании; слепой A/B/X; контекстная подложка с выстрелами.
- **Результат:** из одного проекта за < 10 с получается 6 разных вариантов, которые можно сравнить на равной громкости.
- **Критерии готовности:** 64 кандидата рендерятся за ≤ 10 с (пул процессов); у отобранных вариантов попарное расстояние признаков выше порога; повторная генерация с тем же seed даёт идентичные варианты.
- **Проверка:** тесты детерминизма; слепое прослушивание (не узнаются ли «дубликаты»); проверка выравнивания громкости на тестовых парах.
- **Риски:** метрика различий не совпадает со слуховой — откалибровать веса признаков по оценкам пользователя.

### Этап 5 — ИИ-слой (2–3 недели)

- **Цель:** ИИ меняет звук через те же операции, а человек видит, понимает и правит результат.
- **Функции:** MCP-сервер (`get_project`, `list_node_types`, `analyze`, `propose`, `render`, `compare`); проверка целей после рендера; панель предложений (дифф, объяснение, ✅/❌ целей, A/B; принять целиком, частично или отклонить); журнал с `author: ai`. Первый клиент — любой MCP-клиент (например, Claude Code); встроенная ИИ-панель с адаптерами провайдеров (Anthropic API, OpenAI-совместимый HTTP для локальных моделей) — опционально, в конце этапа.
- **Результат:** сценарий «индустриальный hitmarker, 3 варианта» (раздел 6.5) выполняется от запроса до выбранного и вручную доработанного варианта.
- **Критерии готовности:** ИИ не имеет других побочных эффектов, кроме операций; любое предложение можно откатить одной командой; на наборе из 10 типовых запросов ≥ 7 предложений выполняют свои измеримые цели.
- **Проверка:** набор сценарных тестов с фиксированными исходниками; ручная оценка полезности.
- **Риски:** ИИ ставит цели, которые не соответствуют слышимому результату — нужен быстрый ручной фидбек («лучше / хуже») с записью в журнал; стоимость и латентность вызовов модели.

### Этап 6 — Библиотека и лицензии (1–2 недели; можно параллельно с этапами 2–4)

- **Цель:** легальная, воспроизводимая стартовая библиотека.
- **Функции:** импорт через Freesound API с сохранением снимка лицензии; ручной импорт с обязательными полями; политика при экспорте (CC0, CC BY — да; NC/ND/SA/неясно — блок до согласования); генерация `CREDITS`; внешние справочные библиотеки «только чтение»; браузер библиотеки с фильтром по лицензии и тегам.
- **Результат:** около 20 проверенных CC0/CC BY-ассетов из раздела 3 в библиотеке.
- **Критерии готовности:** экспорт с NC-ассетом блокируется в профиле «распространяемый»; у каждого ассета есть URL, автор, SPDX-лицензия и дата; `CREDITS` содержит все CC BY-предки производного звука, даже через несколько поколений обработки.
- **Проверка:** тесты политики; ручная сверка 20 страниц.
- **Риски:** лицензия на странице может измениться — снимок на дату загрузки решает вопрос происхождения.

### Этап 7 — Профиль Trailblazer и интеграция с Doom-модами (1–2 недели)

- **Цель:** звуки из ForgeSound подходят моду без изменений в моде.
- **Функции:** профиль «Trailblazer» (режимы A/B/C, проверки T1–T10, раздел 6.9): чтение локальной копии мода, экспорт в отдельный каталог, `trailblazer-report.md`; прослушивание с высотами `HitPitch` и «Тестовой серией»; профиль «Doom generic» с `$random`.
- **Результат:** полный комплект одного стиля (например, `TBHITMEA` + `TBKMEA1…5`), прошедший проверки T1–T10.
- **Критерии готовности:** все проверки PASS или WARN с объяснением; громкость в пределах ±1 дБ от текущих файлов (или от явной цели владельца); при попытке экспорта в каталог мода — ошибка.
- **Проверка:** автотесты профиля на копии `src/` мода во временном каталоге; по желанию владельца — запуск UZDoom 5 с временной копией мода и запись звука через OpenAL Soft; финальное прослушивание владельцем.
- **Риски:** UZDoom 5 нет в nixos-26.05 (только 4.14.3) — нужен AppImage или своя деривация; повторный запуск `f10_hitsounds.py` в моде перезапишет перенесённые файлы (вопрос процесса мода).

**MVP = этапы 0–4** (плюс минимальный этап 6): загрузка сэмпла, цепочка обработки, огибающие, слои, вариации, прослушивание, экспорт. **MVP+ИИ = этап 5.** Ориентировочно 3–4 месяца частичной занятости 💭.

💭 Профиль Trailblazer имеет смысл частично подтянуть раньше — сразу после этапа 1 (проверки T1–T6 без UI), чтобы первые звуки MVP сразу сравнивались с реальными файлами мода.

**После MVP:** real-time preview ступенями (раздел 6.12); live-режим через Surge standalone/OSC; хостинг CLAP; перенос горячих узлов в Rust/Faust; упаковка в Tauri; «рецепты» для серий звуков одного стиля (весь арсенал мода в едином звучании).

## 8. Основные риски и нерешённые вопросы

### Технические риски

| Риск | Вероятность / влияние | Что делать |
|---|---|---|
| `surgepy` не собирается в Nix или его API меняется | Средняя / высокое | ✅ Две проблемы сборки уже найдены и обойдены (раздел 2.5); коммит Surge закреплён в `flake.lock`; запасной путь — релиз 1.3.4 без MSEG-API (`devShells.release`) |
| Рендер Surge недетерминирован | ✅ Подтверждено по коду / среднее | RNG засевается от часов. Классы `exact`/`seeded`/`frozen` (раздел 6.3); патч seed в нашей деривации; измерение по типам осцилляторов в S0-3 |
| Скорость массовой генерации вариаций | Средняя / среднее | Пул процессов, «тёплые» экземпляры, кэш по хешу подграфа, черновой режим |
| `pedalboard` / VST3 на NixOS | ✅ Нет в nixpkgs / низкое | Исключён из MVP; эффекты Surge через `surgepy`; позже свой CLAP-хост или Carla как отдельный процесс |
| Realtime-режим в Python не потянет сложные графы | Средняя / среднее | Ступенчатый ввод (раздел 6.12), потоковый контракт узлов с первого дня, перенос горячих узлов в Rust/Faust без смены контракта |
| Устаревший рендер перезапишет новый | Средняя / высокое для доверия к инструменту | Ревизии + `graph_hash`, правило «новое побеждает», видимое состояние (раздел 6.12); тесты в этапах 0 и 1 |
| UZDoom 5 нет в nixpkgs (только 4.14.3) | ✅ Подтверждено / среднее для этапа 7 | AppImage 5.0.3 через `appimage-run` или своя деривация; игровая проверка необязательна для остальных этапов |
| Повторный запуск `f10_hitsounds.py` в моде перезапишет звуки из ForgeSound | Средняя / среднее | Отметить в отчёте экспорта; решение — в процессе мода (не в ForgeSound) |
| WAV с метаданными-чанками не читается движком | Низкая / среднее | Встраивание метаданных в WAV выключено в профиле Trailblazer до проверки в UZDoom |
| Метрики громкости и различий не совпадают со слухом | Высокая / среднее | Калибровка по слепым тестам; несколько метрик в интерфейсе |
| Качество time-stretch и pitch-shift на транзиентах | Средняя / среднее | Предпочитать varispeed; stretch применять только к хвосту |
| ИИ даёт правдоподобные, но плохо звучащие предложения | Высокая / среднее | Измеримые цели, обязательное A/B, быстрый ручной фидбек |
| Audacity 4 так и не вернёт скриптинг | — / низкое | Архитектура от него не зависит (файловый обмен) |
| Лицензии сэмплов изменятся или окажутся неверными | Низкая / высокое | Снимок лицензии при импорте; в распространяемой библиотеке только CC0/CC BY |

### Решённые вопросы (версия 2)

| Вопрос версии 1 | Ответ владельца |
|---|---|
| Лицензия ForgeSound | GPL-3.0-or-later; лицензии зависимостей, плагинов и сэмплов проверяются отдельно |
| Realtime | Оба режима; MVP — render-on-change, архитектура должна допускать real-time preview |
| ИИ-провайдер | Без обязательной облачной модели; заменяемый провайдер, возможна локальная модель |
| Trailblazer | Изучен по репозиторию (раздел 2.4); мод не меняется |
| UI | Локальный backend + браузер; Tauri позже; без облака |
| CC BY | Допускается с автоматическим `CREDITS`; NC/ND/неясное — по согласованию |

### Открытые вопросы

1. **Архив Trailblazer-Extended.** Вложение до сессии не дошло; аудит сделан по репозиторию `Kostr2007/Trailblazer-Extended` @ `888e55a`. Если архив содержит изменения, которых нет в репозитории, их нужно передать ещё раз.
2. **Surge main или релиз.** Для MSEG-огибающих нужен закреплённый коммит main (не релиз). Согласны ли вы на это и на небольшой собственный патч Surge в нашей Nix-деривации (seed для генератора случайных чисел), если S0-3 покажет, что без него не обойтись?
3. **Канал NixOS.** flake закрепляет nixos-26.05 независимо от вашей системы. Есть ли причины ориентироваться на unstable?
4. **UZDoom 5 на NixOS:** как вы его сейчас запускаете (AppImage, Flatpak, своя деривация)? От этого зависит игровая проверка на этапе 7.
5. **Метаданные внутри WAV:** нужно ли встраивать атрибуцию в сами WAV-файлы мода (после проверки в UZDoom), или достаточно `CREDITS` и манифеста?
6. **Сетевой доступ:** для проверки страниц сэмплов и импорта через Freesound API в окружении нужно разрешить `freesound.org`, `opengameart.org` и `kenney.nl` (Allowed domains). Иначе страницы проверяются вручную.
